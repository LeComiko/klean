# Version 0.2.1 : les visiteurs IPv6 sous leur vraie adresse, le code retiré dans l'heure, trois défauts d'affichage

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Corriger les trois limites constatées sur le VPS à la fin du lot A2 (`SPEC.md`, « Lot A2 — fait le 23 novembre 2026 », « Limites constatées »), puis publier la 0.2.1.

**Architecture:** Caddy reçoit un second réseau Docker, `public`, avec l'IPv6 activé sur une plage ULA. Le réseau `klean` reste **identique, octet pour octet**. L'API compte tous ses plafonds par adresse avec `LimiteurDebit.CleDAdresse`, qui regroupe l'IPv6 par /64. La tâche horaire du cron retire le code d'installation à chaque passage, et pas seulement à 3 h. Trois retouches d'écran.

**Tech Stack:** docker compose (Docker 29, Compose v5 sur le VPS), bash (`deploiement/`, séries `tests.sh` et `commande.sh` dans Debian 12), ASP.NET Core 10 + xUnit, React 19 + CSS à la main.

**Version visée :** 0.2.1. L'étiquette décide, rien n'est écrit dans le `.csproj`.

**Relu le 23 novembre 2026** par un spécialiste de Docker. Il a rejoué en local la mise à jour et le retour avec les commandes exactes du `klean` 0.2.0 : aucune ne casse. Ses corrections sont intégrées.

## Ce qui a été mesuré avant d'écrire ce plan (23 novembre 2026)

- **Le défaut.** Sur le VPS, le domaine a un enregistrement AAAA, et Docker écoute sur `[::]:443` par `docker-proxy`, parce que le réseau `klean` n'a pas l'IPv6 (`EnableIPv6=false`). Les sessions ouvertes depuis un Mac et depuis un iPhone, tous deux en IPv6, portent en base `AdresseIp = 172.28.0.1`, la passerelle du réseau. Tous les visiteurs IPv6 partagent donc un même plafond de connexion.
- **⚠️ Activer l'IPv6 sur le réseau `klean` casserait la mise à jour 0.2.0 → 0.2.1.** Reproduit en local avec Compose v5.
  - Compose recrée de lui-même un réseau dont la configuration a changé, mais seulement si aucun conteneur n'y est branché.
  - Or le `klean` 0.2.0, qui conduit la mise à jour (contrat N → N+1), arrête l'API puis lance `compose run --rm migrer` **pendant que Caddy tourne**.
  - Compose essaie alors de recréer le réseau, et Docker refuse : `network … has active endpoints`.
  - La migration échouerait sur toutes les instances.
- **Ce qui marche.** Un conteneur branché sur un réseau ordinaire et sur un **second réseau** avec `enable_ipv6` et un sous-réseau ULA, port publié, voit les vraies adresses. Essai jetable sur le VPS : `traefik/whoami` sur le port 8443, interrogé depuis le Mac, a vu l'adresse IPv6 du Mac en IPv6 et son adresse IPv4 en IPv4. Le pare-feu IPv6 de Docker est actif par défaut depuis la version 27.
- **Un réseau neuf se crée sans conflit** : `compose run migrer` ne touche que `klean`, et le `up -d` qui suit crée `public` puis recrée Caddy.

### Task 1 : Le réseau `public` de Caddy

**Fichiers :** `docker-compose.yml`, `.github/workflows/ci.yml`, `deploiement/klean`, `deploiement/installer.sh`, `deploiement/fonctions.sh`, `deploiement/env.modele`, `deploiement/tests/*`.

- [ ] **Le compose.**
  - **Le réseau `klean` est inchangé** : même sous-réseau, aucune option ajoutée. Un commentaire ⚠️ dit pourquoi : un `compose run` pendant que Caddy tourne échoue dès que sa configuration change.
  - **Un réseau `public` est ajouté :**
    - `enable_ipv6: ${KLEAN_IPV6:-true}` ;
    - **aucun sous-réseau IPv4** : Docker l'attribue de son pool. `public` n'a aucune adresse à connaître, et un sous-réseau fixé pourrait chevaucher un réseau de la machine, ce qui ferait échouer `up -d` pendant une mise à jour, après l'arrêt de l'API. Relu le 23 novembre : mesuré, un réseau dont l'`ipam` ne porte que l'ULA reçoit son IPv4 automatiquement ;
    - un sous-réseau IPv6 **ULA** fixé (`fdXX:…::/64`), tiré une fois au hasard et écrit en dur, selon la RFC 4193 ;
    - **pas de `gw_priority`**, qui exige Engine 28+ et Compose 2.33+ ; une 0.2.0 sur un plugin plus ancien ne lirait plus le compose. La passerelle par défaut de Caddy, ACME compris, est celle que Docker choisit. Mesuré : par `public`. La tâche 7 la relève.
  - **Caddy est branché sur les deux réseaux :**
    - `klean`, avec `ipv4_address: 172.28.0.10` inchangé, pour joindre l'API ;
    - `public`, sans adresse fixée.
  - **L'API, PostgreSQL et `migrer` restent sur `klean` seul.** `Proxy__Reseaux__0` est inchangé : Caddy joint l'API par `klean`, en IPv4.
  - **Vérifier par `docker compose config` que l'interpolation de `enable_ipv6` est acceptée** (booléen interpolé). Si elle ne l'est pas, rendre NEEDS_CONTEXT plutôt que de choisir seul.
- [ ] **Les machines sans IPv6.** Créer un réseau IPv6 sur un noyau où l'IPv6 est désactivé (`ipv6.disable=1`, absence de `/proc/net/if_inet6`) peut échouer. Ce n'est pas mesuré : le dire en commentaire.
  - `fonctions.sh` : une fonction pure `ipv6_disponible`, qui reçoit en paramètre les deux chemins : `/proc/sys/net/ipv6/conf/all/disable_ipv6`, qui doit exister et valoir 0, et `/proc/net/if_inet6`, qui ne doit pas être vide. Avec `disable_ipv6=1`, le second existe mais il est vide. Éprouvée dans `tests.sh` sur les trois cas : disponible, fichier absent, désactivé.
  - **Valider `KLEAN_IPV6`**, qui ne peut valoir que `true` ou `false`. Mesuré : `oui` donne `invalid boolean`, et **toutes** les commandes compose échouent, `klean etat` compris. La validation se fait là où `klean` lit et complète `.env`, avec un refus qui nomme la correction. Une valeur vide retombe sur `true`.
  - `installer.sh` et `preparer_env` écrivent `KLEAN_IPV6=false` si elle répond non, `true` sinon.
  - `env.modele` porte `KLEAN_IPV6=true` : une mise à jour l'ajoute aux `.env` qui ne l'ont pas. La règle d'ajout est celle de `klean` ; la relire.
  - **Limite à consigner, non mesurée :** une 0.2.0 sur une machine sans IPv6, mise à jour par le `klean` 0.2.0, n'aura pas cette détection. Si la création du réseau échoue, ce sera **après** l'arrêt de l'API et la migration. Le remède est `KLEAN_IPV6=false` dans `.env`, puis `sudo klean mettre-a-jour`. Relu : la reprise fonctionne, et un passage de `true` à `false` sur un `public` existant recrée le réseau sans toucher à `migrer`. Le `klean` 0.2.0 est figé : seuls DEPLOIEMENT.md et les notes de version de la 0.2.1 peuvent le dire, et ils le disent.
- [ ] **Le contrat N → N+1**, dans le commentaire de `deploiement/klean` :
  - le réseau `klean` ne change jamais de configuration ;
  - un réseau nouveau est permis, puisqu'il se crée au `up` ;
  - `migrer` ne rejoint jamais `public`.
- [ ] **CI**, dans l'étape qui lit le compose publié en JSON (`jq`), vérifier :
  - `.networks.klean` n'a pas `enable_ipv6`, et son sous-réseau est `172.28.0.0/24` ;
  - `.services.caddy.networks` contient `klean` et `public` ;
  - `.services.api.networks` et `.services.migrer.networks` ne contiennent que `klean`.

  Sabotage : brancher `migrer` sur `public` doit faire échouer l'étape.
- [ ] **commande.sh** : si `klean` lit `KLEAN_IPV6` quelque part, ajouter les cas correspondants. Sinon, rien.

### Task 2 : Tous les plafonds par adresse regroupent l'IPv6 par /64

**Fichiers :** `backend/Controllers/AuthController.cs` (vers la ligne 722), `backend/Controllers/SecondFacteurController.cs` (vers la ligne 383), les tests.

- [ ] **Le problème.** Ces deux contrôleurs comptent par `RemoteIpAddress.ToString()`. Une fois l'IPv6 réelle visible, un seul abonné, qui dispose au moins d'un /64, change d'adresse à chaque essai et sort du plafond de la connexion. Utiliser `LimiteurDebit.CleDAdresse(HttpContext.Connection.RemoteIpAddress)`, comme `InstallationController`.
- [ ] **Ce qui ne change pas :** `ServiceSession` garde l'adresse **brute** dans `AdresseIp`. C'est un renseignement, pas une clé de plafond.
- [ ] **Le test.** ⚠️ Pas sur la connexion d'un seul compte. `ConnexionsParCompte` (10) se déclenche avant `ConnexionsParAdresse` (20), et le sabotage resterait vert (relu). Passer par `POST /api/auth/mot-de-passe-oublie` (`OublisParAdresse` = 3) : quatre requêtes, avec quatre courriels distincts et quatre adresses d'un même /64 (`RemoteIpAddress` posé comme dans `InstallationTests`), rendent un 429 à la quatrième. Témoin : un /64 voisin passe. Pour le second facteur, il faudrait 21 comptes équipés : écrire que ce n'est pas éprouvé de bout en bout, mais par la même fonction.
- [ ] **Sabotage :** remettre `ToString()` dans `AuthController`, et le test rougit.

### Task 3 : Le code retiré à chaque passage horaire

**Fichiers :** `deploiement/klean` (`cmd_sauvegarde_de_nuit`, vers la ligne 213), `deploiement/tests/commande.sh`.

- [ ] **Le problème.** La tâche du cron tourne toutes les heures, mais elle sort avant le retrait hors de 3 h : le code peut rester jusqu'à 24 heures dans `.env` et dans le conteneur.
- [ ] **La correction :**
  - Appeler `retirer_code_si_installe` **avant** le test de l'heure, à chaque passage, 3 h compris.
  - Sa sortie ne doit ni écraser le journal de la nuit (`exec > "$JOURNAL_NUIT"` vide le fichier), ni partir en courrier de cron, **y compris à 3 h**, puisque l'appel précède l'`exec`. Elle va à `logger -t klean`, et seulement s'il y a eu quelque chose à faire. Le cas ordinaire, où il n'y a ni code ni compte, reste silencieux.
  - Un `… | logger` tourne dans un sous-shell, où `KLEAN_VERROUILLE` ne remonte pas. Relu : c'est sans danger ici, car `prendre_verrou -n` est réentrant. Le vérifier.
  - Ne rien recréer sous une opération inachevée : la fonction le garantit déjà, mais il faut le vérifier.
  - Le rattrapage du conteneur (`rattraper_code_de_l_api`) suit la même règle.
- [ ] **commande.sh**, avec un sabotage pour chacun de ces cas :
  - hors de 3 h, avec un code et des comptes : le code part, aucune sauvegarde n'est faite, et le journal de la nuit n'est pas touché ;
  - hors de 3 h, sans rien à faire : aucune sortie ;
  - à 3 h : comportement inchangé.

  `heure_de_la_sauvegarde` et `date` se simulent dans le harnais. Lire comment `commande.sh` simule déjà les commandes.
